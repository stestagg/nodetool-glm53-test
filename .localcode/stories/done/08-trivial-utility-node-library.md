## Description

After story 06 a graph runs and story 07 gives it a voice, but every node that ever ran came from the throwaway example plugins — nothing a real graph would reach for. The vision's product shape lists a first-party library of trivial utility nodes and leaves two questions open: where it lives, and which ones. This story settles both and ships the library.

The settlement, and why: **the utility nodes live in their own first-party plugin crate, not in core.** The requirements permit either — REQ-3 allows core to carry "maybe some trivial utility nodes", and REQ-64/65 say these two "can be part of the core node library" — but permission is not the better product. The plugin-authoring path is the project's central claim (REQ-8, REQ-9): a plugin crate depending only on core, declaring descriptors and behaviour, linking into any binary — and if that path cannot carry even the first-party trivial nodes, it is broken and the project's whole shape with it. These nodes are the canary, so they should live on the path they prove. The boundary it buys is the simplest one to state: core carries *no* node implementations at all — REQ-3's "maybe" is deliberately left unexercised — and every binary opts into the utility nodes by linking one more crate, the same one-line integration step any third-party plugin takes. Nothing in core knows they exist (REQ-73).

**Which ones: exactly the two the requirements name, deliberately no more.** Adding a node later is an ordinary declaration in the utility crate — the library's value is that it exists as a plugin, not its size.

- **If** (REQ-64) — a router, not a calculator. A boolean condition input, a value input, and two outputs, `then` and `else`: each value is routed to exactly one output, chosen by the condition. Both branches stay live and the untouched branch simply receives nothing — values flow as they arrive, nothing waits for its twin (REQ-16).
- **Format** (REQ-65) — the explicit step the type system refuses to do silently. It converts each incoming value to a `String`: with an optional format-string parameter, a template in which the value's string form is substituted at the template's first `{}` (e.g. `"count: {}"`); without it, the plain string form of the value. Automatic conversion to string is deliberately out — REQ-36 declines it, and the vision's scope settles it — precisely so that this node is visible in the graph: a user reading a graph file sees Format at every place a scalar becomes text.

Both are ordinary node types through and through: declared with stable type references, labels, icons, and their own plugin grouping (REQ-10, REQ-42), their behaviour implemented once through story 05's one authoring API and driven by the same uniform driver as every other node — the engine branches on nothing about which node they are. Their value inputs declare the union of the base scalar types (REQ-27); story 04's compile-time resolution does the rest, so a type that neither matches a union member nor arrives by a declared conversion fails to compile with the standard error — a missing Format in the path is a compile error, not a surprise at runtime.

The user here is the plugin author first — these nodes are the first library written the way every future plugin library will be written — and the graph user right behind them: after this story, a graph file can route and format with first-party nodes, and every binary that links the utility crate has them, headless today, in the editor's palette once that exists.

## Definition of done

- The trivial utility nodes live in a separate first-party plugin crate in the workspace whose only dependency is the core crate; it contributes its node types through the one `inventory` registration path and implements behaviour through story 05's one authoring API, with no core modification made for these nodes to exist. Core itself contains no node implementations: a binary that does not link the utility crate enumerates no utility node types — the plugin-less listing stays exactly as story 01 left it. (REQ-3, REQ-8, REQ-9, REQ-73)
- The library contains exactly the two nodes the requirements name — an `If` router and a `Format` node — each declared like any node type: stable type reference, label, icon, its own plugin grouping. Adding another utility node later is an ordinary declaration in the utility crate, not a core change. (REQ-64, REQ-65, REQ-10, REQ-42)
- The If node routes each value to exactly one of its two outputs, `then` and `else`, as its boolean condition selects: a boolean condition input, a value input declared as the union of the base scalar types, values routed as they arrive with no batching or barrier, each routing decision delivering the value to exactly one output — the branch not selected by that decision receiving nothing from it, and neither output waiting on the other; the two outputs declare the same union of base scalar types as the value input, so a routed value flows onward with its resolved type unchanged; it completes by story 05's default rule, so a run containing it finishes normally. (REQ-64, REQ-27, REQ-16, REQ-23)
- The Format node converts each incoming value to a `String`: with its optional format-string parameter, the value's string form substituted into the template at its first `{}` (e.g. `"count: {}"`); without the parameter, the value's plain string form. A value input declared as the union of the base scalar types, a `String` output. No base scalar declares a conversion to `String` (REQ-36) — wiring a base scalar into a `String` input without this node is a compile error, so Format is the only, and visible, step from the base scalars; a plugin custom type reaches `String` only through a conversion its own plugin declared, which stays that plugin's business. (REQ-65, REQ-36, REQ-27, REQ-31)
- Both nodes' behaviours ride story 05's stream semantics unchanged — per-arrival triggering with held-value pairing, default completion — with no second mechanism for either: the If routes by routing, the Format formats by formatting, and neither needs plumbing of its own. The engine drives them by the compiled shape, branching on nothing about which node they are. (REQ-18, REQ-23, REQ-73)
- A connection into either node's value input compiles when the upstream type matches a union member or is bridged by a declared conversion; a plugin custom type reaches Format only through a conversion its own plugin declared to `String`; anything else fails at compile time with the standard error naming both ports and their types. (REQ-27, REQ-35, REQ-71)
- The example binary from the core story runs two sample graph files whose nodes come from the example plugins plus the utility crate — a source feeding an If (its condition held by a parameter literal, `true` in one file, `false` in the other), each branch through its own Format, one with a format template and one without, into consumers. Each run prints every routed, formatted string as it arrives, all of it steered to the branch the condition selects; across the two runs, both branches and both Formats are visibly exercised — the If's steering seen by contrast. Running them (per DEVELOPMENT.md) is the visible proof. (REQ-64, REQ-65, REQ-7)
- Focused tests cover: If routing each pairing decision's value to exactly one selected output — a value whose condition changes after it arrives may appear on both outputs across the run; a value arriving before the condition's first value not firing (story 05's first-value gating); a condition arriving after a value re-routing that held value under the new condition (story 05's held-value pairing); Format with and without the format-string parameter, across several scalar kinds through the union input; both nodes completing when their inputs complete; a connection the union and declared conversions cannot bridge failing to compile; and the empty registry state with only core linked. The workspace builds and passes `cargo test` and `cargo clippy` cleanly.
- DEVELOPMENT.md at the repository root describes the utility crate's place in the layout, how to run the utility-node demonstrations, and the checks.

## Comments

- 2026-09-16 — Home-crate settlement against the requirements: REQ-64/65's "(this can be part of the core node library)" reads as permission, not a mandate, and REQ-3's "beyond maybe some trivial utility nodes" as a bound the design never has to touch. Settling for a separate crate is not a departure — it is the stricter reading of REQ-3 (core carries zero node implementations) and the honest exercise of REQ-8/9's plugin architecture. The cost is one link line per binary, the same integration step every plugin already asks for.
- 2026-09-16 — Unions, not an "any" type: the value inputs of If and Format declare the union of the base scalar types because no "any" type exists in the type model and the system's vocabulary for wide ports is the union (REQ-27). The generic-port idiom ("supports all numeric types", REQ-62) is story 09's settlement; if it yields something better than a spelled-out union, moving these descriptors onto it is an ordinary declaration change in the utility crate — core untouched again. A custom type routes or formats only through a conversion its own plugin declared — the plugin owns its type's path into the system (REQ-32, REQ-34).
- 2026-09-16 — Scope seams: the editor's palette meeting these nodes is stories 11/12 and 19, nothing here — they arrive by the same registry every linked plugin uses. Fizzbuzz's Counter, Condition, and Output are story 09's, not this library's; the fizzbuzz graph (story 10) links both crates. Sub-grouping within the utility plugin is left until the node count asks for it — one node group now, subdivisions when earned. (REQ-10)
- 2026-09-16 — The If node follows story 05's pairing semantics exactly, including the case where the condition arrives after values: a condition arrival triggers processing against the held value, re-routing it under the new condition. That is the one uniform semantics, not a special case this node requests; if real use shows held-value re-routing is wrong for routers, that is a story-05-level conversation, not a carve-out here.
