## Description

Story 11 proved the websocket with a placeholder page; this story replaces it with the real thing: the editor shell the vision's second experience stands on. The user is the graph user who launches the visual mode — until now they could only watch the protocol talk to itself. After this story they open the served address and find an editor: a canvas, a palette of every node type the linked plugins contribute, and the ability to start building a graph by dragging types onto the canvas and arranging them. Building the *connections* between those nodes is story 13; this story is the stage and the first gestures on it.

The shell is the react-flow style canvas under light Blueprint chrome (REQ-45, REQ-50), with the palette docked on the left, keeping the right edge free for the editing sidebar story 14 adds (REQ-56). The palette lists the node types from story 11's listing — every type every linked plugin contributes, drawn straight from the registry so core names nothing specific (REQ-73) — showing each type's label and, as small secondary text, which plugin provides it. Story 19 replaces this plain list with icons, colours, and plugin/sub-group organisation; until then a compact, scrollable list is honest and enough.

Nodes render by the default node class, generated from the type definition so it works when a plugin provides nothing but the definition (REQ-38): a title bar with the node's current label (the type's default; the user-editable override is story 14's (REQ-40, display half only)), input ports down the left, output ports down the right, each port named, the declared type available as a tooltip rather than printed on the node — space is at a premium and the Blender reference keeps nodes compact (REQ-37, REQ-47, REQ-49). Colours, shapes, and icons per type are story 19's.

The interactions this story delivers:

- **Create**: dragging a type from the palette and dropping it on the canvas creates a node instance. The drop becomes an operation message over the websocket — this story's first additions to story 11's catalogue — the server assigns the instance uuid, records the drop position in the node's metadata, applies it to the definition it holds, and pushes the change; the node appears where it was dropped (REQ-46, REQ-41, REQ-12).
- **Move**: a node moves by dragging its title area, the drag itself selecting it; the node follows the pointer for the duration of the drag while one operation commits where it rests — the new position reaching the metadata the same way, operation, server apply, push (REQ-53, REQ-12).
- **Navigate**: background click-drag pans; scroll zooms (REQ-51, REQ-52). Single click selects a node (highlighted); multi-selection is story 20.

The browser holds no authoritative graph state: on load it requests the current definition and renders what the server holds, and every edit lands server-side and is pushed to all connections. A reload, or a second tab, shows the same graph, and a change in one tab appears in the other — one graph state, not two (REQ-2, REQ-45).

Empty states are deliberate, not blank: a first open with an empty definition shows a calm canvas inviting the first node (a short hint, gone once a node exists), and if no node types are linked the palette says so plainly rather than sitting silently empty — and with nothing linked the canvas hint stands down, deferring to the palette's message instead of inviting a first node the palette has just said is impossible.

Deliberately not here: wiring, unhooking, and deletion gestures (13); the sidebar, inline scalar fields, and label editing (14); file load/save (15); start/stop and edit-locking while running (16); live event animation (17); error and connection-loss surfaces (18); palette organisation, icons, and colours (19); multi-selection (20). Until 13 arrives a misplaced node cannot be removed — an accepted gap between adjacent stories, called out so nobody "fixes" it by smuggling deletion in here.

## Definition of done

- Opening the served address shows the editor shell — a react-flow style canvas in the light Blueprint look, with the palette docked on the left and the right edge kept free for the editing sidebar story 14 adds — in place of story 11's placeholder page; the palette lists every node type the linked plugins contribute with its label and providing plugin, sourced from the story 11 listing; with no node types linked the palette states it and the canvas hint defers to that message rather than inviting the first node, while types linked with no node yet get the first-open empty state inviting the first node. (REQ-4, REQ-45, REQ-46, REQ-50)
- Nodes on the canvas render from their type definition by the default node class: title bar with the node's current label, named input ports on the left, named output ports on the right, each port's declared type available as a tooltip; nodes stay compact and carry only the information needed, per the Blender reference. (REQ-37, REQ-38, REQ-40, REQ-47, REQ-49)
- Dragging a node type from the palette onto the canvas creates a node instance at the drop point: an operation message reaches the server, which assigns the instance uuid, records the drop position in the node's metadata, applies the change to the definition it holds, and pushes the change — the assigned uuid reaching the creating client, since the move gesture must address the node it just made; the node appears on the canvas and in the definition. (REQ-46, REQ-41, REQ-12)
- Clicking a node selects it with a visible highlight; dragging a node's title area selects it and moves it — the node follows the pointer for the duration of the drag, and one operation commits the final position, recorded in the node's metadata through the same server-applied operation path; the browser-holds-no-state rule is about authority, not about the gesture waiting on a round trip. Background click-drag pans the canvas; scroll zooms. (REQ-53, REQ-51, REQ-52, REQ-12)
- The canvas renders whatever definition the server holds, empty or not, requesting it on load; a node in the definition whose type reference is missing from the listing still shows — label (its stored override if any, else its type reference) and position, rendered as an inert placeholder with its ports marked unknown — never silently dropped; a node whose metadata carries no position still lands somewhere visible, placed by a deterministic, view-local fallback that every view and reload agrees on, with nothing written into the definition — never invisibly stacked at the origin. (REQ-45, REQ-71)
- The browser holds no graph state of its own: reloading the page or opening a second tab shows the same graph, and a create or move made in one tab appears in the other (last-write-wins per story 11) — edits exist because the server applied them, not because the browser drew them. (REQ-2, REQ-45)
- Focused tests cover the new operation messages server-side: create assigns a fresh uuid and records the position in metadata; move updates it; both apply to the held definition and push to every connection; an operation that parses but cannot be applied — a create naming a type reference no linked plugin provides, or a move naming an instance uuid the held definition does not contain — is answered with an error naming the problem, the definition untouched, per story 11's framing, leaving the connection usable. The workspace builds and passes `cargo test` and `cargo clippy` cleanly, with the UI build part of the check set DEVELOPMENT.md documents.
- The visible proof, run per DEVELOPMENT.md: start the visual example, open it in a browser, drag three node types out and arrange them — panning and zooming away from the default view before one of the drops, that node coming back where it was dropped — reload the page — all three come back in their places — and open a second tab to see the same graph. DEVELOPMENT.md describes how to build and run it.

## Comments

- 2026-09-16 — Scope seams: create and move are this story's additions to story 11's message catalogue, refining 11's comment that grouped all editing operations under 13 and 14 — the gestures live here, so the messages must too; wiring, unhooking, and delete are 13's, sidebar and inline scalars 14's, files 15's, start/stop 16's, events 17's, error surfaces 18's, palette organisation/icons/colours 19's, multi-selection 20's. Nothing here compiles or validates the graph: compile time judges (04), the editor only renders what the definition holds and warns early later (18). (REQ-74, REQ-60)
- 2026-09-16 — UX calls settled here so later stories don't relitigate them: the palette is a plain labelled list until 19 groups and decorates it; the palette docks on the left, keeping the right edge free for 14's editing sidebar (REQ-56); port types live in tooltips, not on-node text, to keep nodes compact (REQ-47); the empty canvas hint disappears the moment a node exists, and when no node types are linked it yields to the palette's message instead of inviting a node; plugin attribution shows as secondary palette text so the user can tell where a type came from without waiting for 19's grouping. Deletion staying out of this story is deliberate — it arrives with 13's gestures as a coherent set (delete node, unhook input) rather than split across two stories.
- 2026-09-16 — The inert placeholder for unknown-typed nodes and the no-stacking rule exist for the state story 15 will create (hand-written files may reference types this binary never linked, and may carry no positions); nothing can produce that state yet, but rendering from the definition must not learn to drop nodes silently first. The UI stays usable when a plugin provides nothing but the definition — the default rendering is exactly for that case. (REQ-38)
- 2026-09-16 — Push shape, settled here so 13, 14, and 20 inherit it rather than relitigate it, and so 17's event stream on the same connection starts from a decided base: server pushes carry the whole updated definition, not the applied operation. The browser holds no graph state of its own — it is a synced view — so a push it can render without applying or merging anything is the one shape that can never diverge from what the server holds, and for a local, single-user graph the bulk is trivial. Operations stay requests; the definition stays the only thing pushed. (REQ-2)
- 2026-09-16 — The canvas gestures — pan, zoom, selection, node drag — build on the canvas library's own interaction primitives rather than bespoke pointer handlers, so 22's accessibility pass adjusts behaviour instead of replacing custom input code: the difference between a pass and a rebuild, decided here.
