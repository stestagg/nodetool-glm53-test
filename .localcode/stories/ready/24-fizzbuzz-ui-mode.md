## Description

Story 10 made `nodetool-fizzbuzz <graph-file>` print the classic sequence to a terminal, and stories 11–22 built the editor that assembles and watches a graph — but the binary and the editor have never met. REQ-69's second mode, and with it the vision's first proof of the whole design, is still missing: launch the fizzbuzz binary and get the visual experience over its own graph, edit it, run it, and still see the output in the console the run's product has always gone to. This story builds that. It is the story REQ-75 points at: when it is done, the fizzbuzz crate "works as intended", and the same graph file demonstrably serves both doors — the terminal's and the editor's.

The outcome, as the user sees it: `nodetool-fizzbuzz --ui graphs/fizzbuzz.yaml` starts the core server (11) hosting the editor (12–22), prints the address it serves on, and the browser that address is opened in shows the fizzbuzz graph already on the canvas — nodes placed by their metadata, chrome naming the file (15's launch-with-file behaviour, the same loader and the same seeding path). Editing is the editor's, whole: drag, wire, value, rename, save. Press Start and the run compiles from the held definition (16) — the canvas animates (17) while the terminal prints `1, 2, Fizz, 4, Buzz, …` as the values arrive, because the printing rule story 10 settled — every unconnected output delivered to the terminal, one line per value, in arrival order, plain string form — is the same rule REQ-69's "still printing the output to the console" asks for, and this story is where it gets wired to editor-started runs (16's comment reserved exactly this wiring). Stop mid-run and the printing stops with the run; change the Counter's stop from 100 to 20 and the next start prints the edited sequence; a graph that no longer compiles shows 16's compile errors and never starts. Headless stays headless: without `--ui` the binary is story 10's, untouched.

Two settlements, made here because this is the story that has to live with them:

**The console gets its values through one general seam, not a fizzbuzz path.** In headless mode the binary itself builds the run and attaches the terminal to the unconnected outputs (06's consumer mechanism, one more downstream of the fan-out). In UI mode the server builds the run — start arrives as a command (16) — so the values on unconnected outputs are inside the server unless the host is let in. The settlement: the server accepts an optional unconnected-output consumer from the binary that hosts it, carried to each run it starts — the engine's one consumer mechanism (06) reaching through the server, no second path and no per-binary branch anywhere in core (REQ-73). The fizzbuzz binary supplies the terminal printer, story 10's rule verbatim; the editor example supplies none and keeps discarding (06), unchanged; a host supplying nothing changes nothing. This is also why the shipped graph's product still reaches the terminal in UI mode: the case-selection node's output is unconnected, so the printing rule — not the Output node's vec, which stays the program-facing collector stories 09 and 10 settled it to be — is what prints.

**The process boundary gets the guard the editor already has.** Stories 15 and 16 both handed this story one decision: whether Ctrl-C on a binary holding an unsaved graph simply loses it. The settlement is the same guard 15 placed where loss is real, extended to the process edge: Ctrl-C with unsaved changes (the dirty state 15 made server-known) prints a warning naming the situation and stands down — a second Ctrl-C quits immediately, the user's way of saying they know; with nothing unsaved, Ctrl-C quits promptly. A browser tab closed mid-edit is still the browser's own edge — 15's in-editor confirm covers replacing the graph, this covers the process, and nothing here invents a third protection between them. Recorded as a decision rather than an oversight, per both handovers.

Deliberately not here: start/stop, the run lock, recompile-per-start, and run outcomes (16); the canvas animation and mid-run attach (17); toasts and connection-loss surfaces (18); custom node UI (21); groups (23). The binary links the same crates story 10 linked — the utility crate stays out, the palette showing the fizzbuzz nodes this binary exists to serve; a user wanting If and Format in this palette is a later, separate call. No `--port` or address flags, no auto-opened browser: the address is printed, opening it is the user's one gesture, and nothing gets a knob until a run asks for it (10's posture). And the Output node, if a user drops one, behaves exactly as its settlements say — values collected in its vec, nothing printed — the terminal rule being about unconnected outputs, of which the Output node has none.

## Definition of done

- `nodetool-fizzbuzz --ui <graph-file>` launches the visual mode: the core server (11) starts on its loopback default, the graph file is loaded through the story 03 loader into the server-held definition — story 15's launch-with-file seeding, so unpositioned nodes land on the deterministic fallback and unlinked types render as inert placeholders — and the served address is printed to the terminal. Opening it in a browser shows the editor with that graph on the canvas and the chrome naming the file; editing, saving, opening, and fresh-graph work as stories 12–15 and 22 built them. (REQ-69, REQ-4, REQ-11)
- `nodetool-fizzbuzz --ui` with no file launches the same editor on an empty, untitled canvas, story 15's launch rule; the bare binary with no `--ui` and no file answers with a usage error naming the graph file argument it expected, on stderr, with a non-zero exit — settled here rather than cited, story 10's record covering a file path that is missing or fails to load or compile, not an invocation with no argument at all, REQ-68 making the file the headless contract; and without `--ui` the binary is the headless path exactly as story 10 shipped it, printing unchanged. (REQ-69, REQ-68)
- While a run started from the editor is on, every value arriving on an output the graph leaves unconnected prints to the terminal as it arrives — one line per value, in arrival order, in its plain string form, on stdout, nothing buffered to the run's end — story 10's printing rule inherited whole; a completed, failed, or stopped run ends the printing, and the next start prints afresh. The fizzbuzz proof: launching UI mode on the shipped graph and pressing Start prints the classic sequence — 1, 2, Fizz, 4, Buzz, …, 14, FizzBuzz, …, 98, Fizz, Buzz — exactly 100 lines, in count order; the shipped run is a burst too short for a human to watch, so the canvas animating belongs to the visible proof's longer run, not this bullet, and the unbuffered arrival stays the focused tests' property, story 10's incremental test inherited. (REQ-69, REQ-75)
- The values reach the terminal through one general seam: the server lets its hosting binary supply the consumer for the unconnected outputs of the runs it starts — the engine's consumer mechanism (06) carried through, an attached consumer one more downstream of the same fan-out — with core naming nothing specific to any plugin, node, port, or output, and a host supplying none keeping story 06's discard, the editor example unchanged. (REQ-73, REQ-2, REQ-69)
- A graph file argument that is missing, unreadable, or unparseable in UI mode ends the launch with the error printed to stderr — naming what and where — and a non-zero exit, no server started: the load stage of the same judgement the headless path makes, so one file meets one rule at load whichever mode asks — compile stays start's (16), where headless judges it before running; errors raised after launch — editor-side open and save failures, compile errors on start, run failures — stay the editor's surfaces (15, 16, 18), the session continuing. (REQ-71, REQ-69)
- Ctrl-C with unsaved changes prints a warning naming the situation and does not quit; a second Ctrl-C quits immediately; with nothing unsaved the first Ctrl-C quits promptly. The unsaved state is the server-known dirty state (15) — set by edits, cleared by open, save, and fresh-graph — and the guard is the process-boundary twin of 15's in-editor confirm, the one 15 and 16 handed here to settle.
- Editing and running in UI mode behave as the editor stories built them, over the binary's own linked nodes: the palette lists the fizzbuzz node types from the registry, Start compiles the held definition afresh and runs it, the lock quiets editing while it runs, outcomes tell completed, failed, and stopped apart, and what runs is always what was last edited. (REQ-69, REQ-26, REQ-25, REQ-22)
- Focused tests cover: `--ui` launching with a file seeding the held definition through the story 03 loader and with no file starting empty; the launch-path load errors exiting non-zero with the message and no server started; the supplied consumer receiving each editor-started run's unconnected-output values in arrival order while a connected output's values reach only their wired downstream; a host with no consumer discarding per 06; the printed lines matching the plain string form; the quit guard's three paths — clean prompt exit, warn-and-stand-down, second-Ctrl-C force exit — as the guard's decision against the server-known dirty state, the real keystrokes exercised in the visible proof below; and the headless path regressing none of story 10's tests. The workspace builds and passes `cargo test` and `cargo clippy` cleanly, with the UI build part of the check set DEVELOPMENT.md documents.
- The visible proof, run per DEVELOPMENT.md: launch `nodetool-fizzbuzz --ui graphs/fizzbuzz.yaml` and open the printed address — the fizzbuzz graph is on the canvas, the chrome names the file. Set the Counter's stop to a large value, one the run lasts over, and press Start — the terminal streams the sequence while the canvas animates, both views of one run; press Stop mid-run — printing stops, stopped shows. Set the stop to 20 and start again — 20 lines, the edited definition; relaunch on the untouched shipped file and press Start — the classic sequence, 1, 2, Fizz, 4, Buzz, …, 98, Fizz, Buzz, exactly 100 lines in count order. Wire something that fails to compile and press Start — the compile errors show, no run, editing still free; fix it and start again — clean. Make an edit and Ctrl-C — the warning stands down; Ctrl-C again — gone; relaunch, change nothing, and Ctrl-C once — gone. And run `nodetool-fizzbuzz graphs/fizzbuzz.yaml` headless once more — the same 100 lines, the same graph through the other door. DEVELOPMENT.md describes both invocations and the checks.

## Comments

- 2026-09-16 — Scope seams: this story adds no message to story 11's catalogue and no engine behaviour — the seam it needs is the server carrying its host's consumer to the runs it starts, 06's mechanism unchanged; start/stop, the lock, outcomes, and recompile-per-start are 16's, animation and mid-run attach 17's, error surfaces 18's, files 15's, groups 23's. The console printing inherits story 10's rule — 10's comment reserved the UI-mode application for this story, and 16's comment reserved the wiring; the editor example keeps discarding. 15 and 16 both parked the process-exit guard here; settled above, recorded as this story's call. The editor example linking the fizzbuzz crate is story 17's doing, so the Counter reaches that palette there; this story is the fizzbuzz binary hosting the editor itself, its palette its own linked nodes. (REQ-74)
- 2026-09-16 — UX calls settled here: one `--ui` flag rather than subcommands or a second binary — the mode is one word added to the command the user already knows, and the file argument means the same thing in both modes; the graph file optional in UI mode because the editor is an editing environment and story 15 already gives it the empty-canvas start, while headless keeps the file required — its whole contract is "run this file"; the bare invocation with neither `--ui` nor a file answers with the usage error the DoD settles — a case story 10's record does not cover, its error path starting at a file path that fails, so the call is made here, `--ui` being what makes the file optional anywhere; the address printed rather than a browser auto-opened — one printed line is honest and quiet, auto-open is platform ceremony; and the quit guard is the double-Ctrl-C convention, force-exit on the second, because a guard that cannot be overridden is worse than none and a warning that cannot be silenced is nagging. The utility crate stays unlinked — the palette serves the graph this binary exists for; growing it is a separate product call if anyone makes one.
- 2026-09-16 — Why the consumer seam is general and host-supplied rather than a "print in UI mode" feature: story 10 settled the printing rule once, on purpose, and the same rule serving both modes was its stated intent; the alternative — the server learning to print, or learning about stdout — puts a terminal into core and a fizzbuzz-shaped fact beside it (REQ-73). The server's job stays: hold the definition, start runs; what the host does with a run's product is the host's, exactly as headless has been. The Output node's vec stays program-facing per 09 and 10 — nothing here reads it, and a dropped Output node collecting silently is its settled behaviour, not a gap.
- 2026-09-16 — The quit guard carries no REQ id: REQ-69 does not ask for it, nor any other line — it stands on 15's placement argument (the guard lives where loss is real) and on both stories' handover, recorded so it reads as the deliberate settlement it is. The process exit code stays story 10's in headless; in UI mode a clean quit exits zero and a launch failure exits non-zero, a mid-session failed run not being a process failure — the editor told the user, and the session is the thing whose success the exit code reports.
