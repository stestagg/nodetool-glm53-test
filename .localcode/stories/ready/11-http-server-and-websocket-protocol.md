## Description

After story 10 a graph file runs headless from a terminal, but the vision's second experience — the visual one — has nothing to stand on: no server, no editor, no path between the engine and a browser. Stories 12 onward build the editor; this story builds what it stands on: the small HTTP server core owes the product (REQ-4), the websocket it speaks, and the protocol shape the editor stories will fill in. The user here is the graph user launching the visual mode: after this story they can start the server and open it in a browser and find it alive — a page that connects, greets, and answers. Not the editor yet; that is story 12's. The thing it will talk to, proven end to end.

The websocket protocol shape is one of the vision's open questions, and this story settles it deliberately:

- **One connection carries everything.** The browser opens a single websocket and every exchange travels it: requests, replies, state updates, and — later — engine events. No REST side-channel, no second socket. One address to open, one thing to lose and surface (18), one mechanism (REQ-2).
- **The server owns the graph.** The server holds the in-memory graph definition — the story 03 document, the same shape the compiler takes (04) — and the browser is a synced view of it. Edits are operations sent to the server, applied there, and the resulting change pushed to every connection. This is what makes compile (16), run (16), and file save (15) server-side truths that can never diverge from what the user sees, and it means a reloaded or reopened browser simply asks for the definition again — the state survives the browser, not the other way round. The tool is single-user and local: a second tab is another view of the same graph, edits land last-write-wins, and there is no locking, presence, or merge ceremony to build.
- **A JSON envelope, and an additive message set.** Every message is a JSON object with a type; browser-to-server messages carry an id the reply echoes; a reply is either the answer or an error naming the problem; server pushes ride the same envelope with no id. The full catalogue cannot be known before the editor stories exist, so what settles here is the framing that keeps additions cheap: this story ships the greeting and the two backbone requests — the node-type listing and the current definition — and each editor story adds its operation messages additively, changing nothing at the framing level.
- **Malformed input is reported, never fatal.** The websocket is untrusted input at a parse boundary, exactly as the vision's security posture says: a message that fails to parse, is not a JSON object, names an unknown type, or carries unknown fields is answered with an error naming the problem, the connection stays open, and no input can crash or corrupt the server.
- **Loopback by default.** The server binds loopback on a default port; the binary hosting it may offer the address and port. No auth, no remote posture — the vision's scope is deliberate here.
- **Bulk things travel as assets, not messages.** Anything bulky a plugin or the UI ships — custom UI assets chief among them — reaches the browser served by this HTTP server, not packed through protocol messages. The plugin-facing mechanism is story 21's, built on this seam.

Event streaming needs one more sentence: the push channel this story builds is the path engine events will take to the editor. The bridge from story 07's observer — starting runs, forwarding events, and deciding how much value data to thin — is stories 16 and 17; nothing here runs a graph.

## Definition of done

- The core crate carries a small HTTP server that binds loopback by default on a default port and serves its embedded UI assets over HTTP, with the websocket endpoint on the same address — one address to open. Nothing about a binary changes unless it starts the server: the headless path (06, 10) uses none of it. (REQ-4, REQ-7)
- The protocol is one websocket connection carrying every exchange in the JSON envelope: a browser message carries a type and an id its reply echoes; a reply is either the answer or an error naming the problem; an error echoes the id of the request it answers, and an error to a message too malformed to carry one has no id; server pushes ride the same envelope with no id; unknown message types and unknown fields are errors, not silently ignored keys. The framing is the settled shape — editor stories add messages additively without changing it. (REQ-45, REQ-2, REQ-71)
- On connect the server pushes a greeting naming the protocol version and the graph schema version (03) it speaks, so a mismatch is visible rather than silent. Two requests ship with this story: the node-type listing — every node type the linked plugins contribute, with its type reference, label, inline svg icon, plugin group, sub-group, and ports with their declared type references, straight from the registry and naming nothing specific to any node or plugin — and the current graph definition: the whole story 03 document serialised as JSON under the same schema, parameters, edges, and metadata carried verbatim. The listing is the palette's data source, its type reference the key every later editing operation names a node type by; the definition request is what a reloading browser makes to resync. (REQ-8, REQ-10, REQ-11, REQ-42, REQ-73)
- Any message that fails to parse as JSON, is not a JSON object, names an unknown type, or carries unknown fields is answered with an error reply naming the problem; the connection stays open; the server survives arbitrary garbage without crashing or corrupting its state. (REQ-71)
- Server pushes are the settled transport path engine events will take to the editor: the channel exists and is exercised by the greeting push — this story's only push, as nothing here yet changes state — while the listing and the definition travel as replies to requests on the same channel. No message here yet broadcasts, so the fan-out the engine events will ride is the server's push API, tested directly. The observer bridge, run commands, and thinning policy are stories 16 and 17, which must fit this path rather than add a second one. (REQ-14, REQ-13)
- A workspace example binary linked with the example plugins starts the server and prints the address; opening the served page in a browser shows the connection live — the greeting, the listing of the linked plugins' node types, the current (empty) definition — and typing a malformed message into the page produces a visible error reply while the connection carries on. The page is this story's placeholder view of the protocol, replaced by the editor shell in story 12. Running it (per DEVELOPMENT.md) is the visible proof. (REQ-4, REQ-71)
- Focused tests cover: the envelope round trip — a request answered with the matching id; the greeting's versions; the listing matching the registry for the linked plugins; the definition request returning the server's in-memory definition verbatim, the test seeding that state through the server's own API; each malformed path (bad JSON, non-object JSON, unknown type, unknown field) answered with an error and leaving the connection usable; several connections each receiving one broadcast issued through the server's push API; and the loopback default bind. The workspace builds and passes `cargo test` and `cargo clippy` cleanly.
- DEVELOPMENT.md at the repository root describes how to run the server example and the checks.

## Comments

- 2026-09-16 — Scope seams: the editor shell that replaces the placeholder page is 12; the editing operation messages (create, move, wire, unhook, delete, parameter edits) are 13 and 14's additions to the catalogue; loading and saving graph files is 15; start/stop is 16, with 17 bridging engine events and settling how much value data the transport forwards; connection-loss UX in the browser is 18, and whether a browser can reattach to a running run is 17's call — the state that survives here is the definition, not a run. Custom UI asset delivery is 21 on this same server; the palette's presentation of the listing is 19. (REQ-74)
- 2026-09-16 — Why the server owns the definition: compile, run, and save are all server-side acts, so browser-held state would always be one decision away from diverging from the run. Server authority also gives the deliberate empty canvas (12) and the reload-resync for free. Last-write-wins across tabs is the honest rule for a local single-user tool; anything stronger is ceremony the vision's scope excludes.
- 2026-09-16 — REQ-14 is split as a refinement of story 07's record: story 07 left the bridge to the transport and editor stories; this story takes only the transport path, 16 the start/stop that triggers events, 17 the live visualisation. The citation here covers the path, not the experience. (REQ-14)
- 2026-09-16 — Two serialisations, one model: files are YAML (03, hand-written and versioned), the protocol is JSON (machine-to-machine inside one binary pair, where the browser lives natively). Both serialise the same in-memory definition — no second graph representation enters the codebase. Whatever schema room 23's groups need in files rides the same message untouched. (REQ-44)
- 2026-09-16 — Unknown fields in protocol messages are errors, mirroring the file format's honesty: a typo'd message should be visible, not swallowed. The accepted cost is that a client speaking a message the server does not know is rejected outright — tolerable because one binary serves its own UI, and the additive rule (new types, never changed framing) is the growth path if that ever stops being true. REQ-72 warns against added failure modes; this one is the deliberate exception, argued here rather than cited as support.
