## Description

Stories 01–07 built the machinery and story 08 the first first-party plugin library, but the vision's proof of the design — the fizzbuzz example — still has nothing to stand on: no `nodetool-fizzbuzz` crate, and no Counter, Condition, or Output for its graph to reach for. The requirements name exactly what the example needs (REQ-61 to REQ-63, REQ-66, REQ-67); this story creates the crate and its node library, and settles the one open question the vision left hanging: how a node definition expresses generic numeric ports — a Counter that supports all numeric types — without per-type duplication.

The user here is the plugin author first — these nodes are the first library written against the generic-port idiom — and the graph user right behind them, whose fizzbuzz run is story 10's.

The settlement, and why: **one node type per node, its generic ports declared as a type family the compiler unifies at compile time.** A Counter is one node type in the registry — not ten — whose start, stop, step, and output ports together declare the base numeric set (REQ-27, REQ-29); the compiler resolves the family to one concrete type from the instance's connections and parameter literals, under the same exact-or-declared-conversion rules every connection already follows (REQ-28, REQ-35). A family the instance's sources cannot agree on fails to compile with an error naming the ports and their types, and so does a family with no resolution source at all — nothing connected, no literal — which otherwise would be a node that silently never runs. Compile time is the right place: the vision promises a run never starts on a broken graph, and a Counter whose start is fed from a `u64` source while its stop is an `f64` literal is ill-defined, not merely inconvenient — no declared conversion joins them (the base set declares only `i16`→`i32`, `f32`→`f64`, `i32`→`f64`) — failing before the run beats discovering it mid-stream (REQ-71). At runtime the behaviour receives the resolved type and reads values as that concrete Rust type; no runtime dispatch, no second mechanism (REQ-2). The author writes each node's numeric logic once — a small plugin-side helper in the fizzbuzz crate stamps the descriptor and the per-type behaviour from one generic body — and core gains only the general family mechanism and a general way for a node type to have its parameters validated at compile time, both naming no node and no type (REQ-73). The utility crate's spelled-out unions (story 08) stay as they are; adopting the idiom later is an ordinary declaration change there.

Then the nodes themselves:

- **Counter** (REQ-62) — a self-driving source. Once it holds a start, stop, and step (in the fizzbuzz graph, parameter literals), it emits start, then start+step, and so on through stop, then completes when the sequence is exhausted — per story 05's source rule (a node whose logic produces on its own schedule drives itself and completes when exhausted), independent of its inputs' completion. It iterates once: a later-arriving start/stop/step value is simply of no effect — not a restart, not an error. Basic range checking as the requirement asks: a step of zero is rejected — at compile time when step is a literal, as a behaviour error when values stream in — while an inverted range (a stop the step's direction never reaches) is simply an empty stream that completes; rejecting it would be an extra failure mode, so none is added (REQ-72).
- **Condition** (REQ-63) — two numeric inputs of one resolved type and a `bool` output; each instance applies its operation — equality, inequality, less-than, less-or-equal, greater-than, greater-or-equal — per story 05's pairing semantics, completing by the default rule. The operation is specified by which Condition type the instance instantiates: one Condition per operation, stamped from the one shared behaviour, grouped under a condition sub-group. A per-instance operation *setting* — the dropdown a Blender-style editor might show — would be a new descriptor concept and a file-format field with exactly one consumer today; that is speculative generality now, so the six declarations carry it, and the settings question stays deliberately open for the editor stories to settle if wanted.
- **Output** (REQ-66) — the terminus: a `String` input, no outputs, collecting every string that arrives in arrival order, completing when its input does; the collected vec is the node's own state, its collection proven here by this story's tests driving the behaviour directly, and how a consumer reaches it — the run-end retrieval seam — is story 10's settlement. Printing values as they arrive (REQ-68) is the events stream's and consumption path's job, not this node's.

The crate is a binary crate in the workspace from the start (REQ-61, REQ-67) — the shape the vision gives fizzbuzz — with headless mode, the graph file, and the run still ahead of it in story 10; the editor's meeting with these nodes is stories 12 and 19.

## Definition of done

- A new `nodetool-fizzbuzz` binary crate in the workspace links core and registers its node types through the one `inventory` path; running its binary lists what it contributes — one Counter, the six Condition operations, one Output — each with its ports and the concrete set of types each port spans — for the Counter and Condition, the numeric members of the family — not a family marker or shorthand. Running it (per DEVELOPMENT.md) is the visible proof that the crate and its library exist and link in like any plugin. (REQ-61, REQ-67, REQ-8)
- The generic-numeric settlement: core's node/type model gains a general way for a node type to declare a set of its ports as one family resolved to a single concrete type at compile time; the Counter and Condition are declared through it, and the registry enumerates no per-numeric-type duplication: one Counter descriptor, six Condition descriptors — one per operation, stamped from the one shared behaviour — and one Output. A plugin-side helper in the fizzbuzz crate lets the author write each node's numeric logic once and stamps the descriptor and per-type behaviour from it; nothing repeats per type, and core gains only the general family mechanism and the general compile-time parameter-validation hook — validation a node type's plugin supplies and the compiler consults through the registry — neither naming a specific node or type. (REQ-62, REQ-63, REQ-5, REQ-73)
- A family resolves at compile time from the instance's connections and parameter literals under the connection rules — exact match, or one declared conversion bridging to the family's type; when several family members are reachable, resolution stays deterministic: an exact agreement wins, otherwise the first declared family member every source reaches by one declared conversion, walking the family's declaration order, never registry order (story 04's union tiebreak). Sources that cannot agree on one type fail to compile with an error naming the node, the ports, and their types, as does a family with no resolution source. The resolved type is recorded on the compiled node, and the behaviour receives values as that concrete Rust type — no runtime type dispatch anywhere. (REQ-28, REQ-35, REQ-71)
- The Counter emits start, then start+step, and so on while the accumulated value has not passed stop in step's direction — stop included when the accumulation lands exactly on it — then completes with its sequence exhausted, per story 05's source rule; later-arriving start/stop/step values are of no effect and do not restart it. A step of zero is rejected at compile time when step is a literal, and raises a behaviour error when it streams in; an inverted range yields no values and completes. (REQ-62, REQ-71, REQ-72)
- Each Condition instance compares its two inputs — one resolved numeric type — and emits the boolean result as values arrive, per story 05's pairing semantics, completing by the default rule when its inputs complete. (REQ-63, REQ-18, REQ-23)
- The Output node accepts `String` values only — anything else fails to compile into it, except a plugin custom type reaching `String` through a conversion its own plugin declared, which stays that plugin's business, as story 08's Format criterion carries — so Format remains the visible step; it collects values in arrival order and completes when its input completes, the collected vec remaining the node's own state, its run-end retrieval seam story 10's settlement. (REQ-66, REQ-23, REQ-36)
- All three are declared like any node type: stable type references, default labels, svg icons, plugin grouping with the conditions under their own sub-group. (REQ-10, REQ-42)
- Focused tests cover: family unification — same type, a declared conversion bridging, several family members reachable resolved by the declaration-order tiebreak, conflicting sources failing to compile, a source-less family failing to compile; the Counter's sequence including the inverted-range and step-zero cases, literal and streamed, completion after exhaustion, and no-restart — later-arriving start/stop/step values after exhaustion leaving the node complete and its sequence unchanged; a Condition across several numeric types with each operation; the Output's collection order; and the Counter and Condition descriptors' port type sets naming the family's numeric members. The workspace builds and passes `cargo test` and `cargo clippy` cleanly.
- DEVELOPMENT.md at the repository root describes the fizzbuzz crate's place in the layout, how to run its node listing, and the checks.

## Comments

- 2026-09-16 — Scope seams: the graph file, headless mode, the printing, and the vec's consumer side — including the run-end retrieval seam — are story 10; interactive start/stop and the UI mode are stories 16 and 24; the palette's presentation of these nodes is 19; custom node UI is 21. Nothing here runs a graph — story 05's single-node driver and the compiler prove behaviour and resolution, and story 10 remains the first end-to-end fizzbuzz run. An inverted literal range surfaces in the editor as a Counter that runs and completes with nothing to show — correct streaming truth here, and a natural warn-early candidate for story 18's set. (REQ-74)
- 2026-09-16 — The Condition operation question, settled openly: the requirements' model has no per-instance settings concept — descriptors carry ports, and files carry parameters, which are port literals — and inventing one for a single consumer is the speculative generality the vision forbids. Six declared operations from one shared behaviour cost nothing to build and read clearly in a graph file; if the editor stories (12–14, 21) later want a single Condition with an operation control, the settings mechanism should be designed then, in the open, for its real set of consumers.
- 2026-09-16 — "All numeric types" means the base numeric scalars the type model ships (story 02's set); the family's membership is the plugin's declaration, so a later scalar joins by extending it — an ordinary declaration change, not a core one.
- 2026-09-16 — The Output's vec is the run's collected product, not a port value: exposing it as a stream value would drag a list type through the value representation and force a custom type for one node's sake. Its collection is this story's; the run-end retrieval seam — how a consumer reaches the vec — is story 10's settlement, made in the open, and when it lands it must be a general run capability — a node type may expose a run-end product, addressed by node instance uuid, with core branching on nothing about which node it serves — not an output-node special case. (REQ-73)
