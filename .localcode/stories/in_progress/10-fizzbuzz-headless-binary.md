## Description

Everything the design promised now exists in parts: graphs are files (03) that compile (04), nodes have behaviour under streaming semantics (05), whole graphs run headless (06) with an event voice (07), the utility library ships If and Format (08), and the fizzbuzz plugin declares Counter, Condition, and Output (09). Nothing yet ties it together into the thing the vision holds up as the proof: type `nodetool-fizzbuzz <graph-file>`, and the classic fizzbuzz prints, line by line, as the graph produces it. This story builds that.

The outcome, as the user sees it: a `nodetool-fizzbuzz` binary whose headless mode takes a graph file path, loads it (03), compiles it (04), runs it (06), and prints the run's outputs to the terminal as they arrive — one line per value, nothing held back to the end. The binary is a generic headless runner: any graph file its linked nodes can express runs the same way, so a user can hand-write a variant — a counter to a million, say — and watch lines stream. The shipped proof is the fizzbuzz graph itself: a hand-written YAML file in the story 03 format, using parameter literals for the Counter's bounds and the Conditions' divisors, whose run prints 1, 2, Fizz, 4, Buzz, …, 14, FizzBuzz, … 98, Fizz, Buzz — exactly one hundred lines, in order.

Two settlements make the graph trustworthy rather than merely plausible; both are made here because this is the story that has to live with them:

**The graph keeps the per-count string on a single serial path.** The obvious fizzbuzz wiring — the count fanning out into Conditions and If routers, four case branches of Formats merging at the sink — does not survive the stream semantics this project has settled. Held-value pairing (05) pairs each arrival with the *latest* held value of a node's other inputs, and the engine lets independent fan-out branches run at their own pace: a router fed by a divisibility stream and the count stream can pair a count with a stale condition and re-route it later, duplicating values across branches — the exact behaviour story 08 documents for If. And even correctly paired branches that merge cannot promise count order at the merge, because nothing in a streaming engine serialises parallel branches. So the fizzbuzz plugin gains one more node beside story 09's three — a case-selection node fed by the count and the two divisibility streams, which aligns the three per-count streams (story 05 explicitly provides the escape hatch: a node whose pairing needs more than the default consumes its inputs' arrivals directly) and emits each count's fizzbuzz string in count order onto its output — left unconnected, so settlement 2's terminal is its consumer. One path, one ordering: the sequence correct by construction. The Conditions feeding it test divisibility — `count % 3 == 0` — which story 09's six operations do not include and which no arithmetic node anywhere in the named set could compose, so the plugin gains that operation too, an ordinary declaration in the plugin, the extension path story 09 designed — with a behaviour of its own, the shared condition behaviour's re-emit on a divisor arrival being one boolean too many for the per-count alignment. The additions live in the plugin, not core — plugin-specific concerns, per the boundary.

**The terminal is the consumer of everything the graph leaves unconnected.** Headless printing has one rule, no configuration: every output port with no downstream connection in the graph is delivered to the terminal, one line per value, in arrival order, each value in its plain string form — the Format node's without-template behaviour. Values go to stdout; errors — a missing file, a file that fails to load or compile, a run that ends in an error — go to stderr with a non-zero exit, naming what and where, never a panic or a backtrace. No event timeline by default: the run's product travels the data path (06); the observer (07) stays available to whoever wants diagnostics, and no knob is added until someone asks.

## Definition of done

- The workspace contains the `nodetool-fizzbuzz` binary crate, depending on the core crate and registering the plugin's node types through `inventory`; no core change is made for its sake, and the binary links only what its graphs need. (REQ-61, REQ-67, REQ-8, REQ-73)
- Running the binary with a graph file path runs the headless path with no UI involved: the file is loaded (03), compiled (04), executed (06), and each value arriving on an output the graph leaves unconnected is printed to the terminal as it arrives — one line per value, in arrival order, each in its plain string form (the Format node's without-template behaviour), nothing buffered until the run ends. (REQ-68, REQ-7, REQ-2)
- The crate ships a hand-written fizzbuzz graph file in the story 03 format: a Counter iterating 1 to 100, Condition instances testing divisibility by 3 and by 5 (the Counter's bounds and the divisors carried as parameter literals), and the plugin's case-selection node whose inputs are the count and the two condition streams and which emits each count's fizzbuzz string in count order, its output left unconnected for the terminal rule to print. Running it (per DEVELOPMENT.md) prints the classic sequence — 1, 2, Fizz, 4, Buzz, Fizz, …, 14, FizzBuzz, …, 98, Fizz, Buzz — exactly 100 lines, in count order, by the printing rule. (REQ-62, REQ-63, REQ-11, REQ-68, REQ-75)
- The case-selection node is part of the fizzbuzz plugin crate, added by this story: it aligns its per-count input streams by their shared arrival order and emits exactly one string per count, in count order; the Conditions' outputs feed it and its output is the one the graph leaves unconnected, so the printed order is the count order by construction. (REQ-73, REQ-75)
- The divisibility Condition is this story's addition to the fizzbuzz plugin crate, declared beside story 09's six. The graph needs `count % 3 == 0` and `count % 5 == 0`; the settled six operations do not include divisibility, and no arithmetic node exists anywhere in the named set to compose it — so the plugin declares the operation through the ordinary extension path story 09 designed, with a behaviour of its own: the shared condition behaviour re-emits on a divisor arrival, and the per-count alignment cannot survive a second boolean per count. (REQ-63, REQ-73, REQ-75)
- The streaming is observable: printing happens through the run's data path as values arrive, not as a run-end dump; a hand-written variant of the shipped graph with a longer counter range visibly streams line by line rather than appearing at once at the end. (REQ-16, REQ-68)
- A graph file that is missing, fails to load, or fails to compile ends the run with that error printed — naming what and where — and a non-zero exit status; no panic and no backtrace reaches the terminal. (REQ-71)
- The headless run is covered by tests: the shipped graph's full 100-line sequence asserted end to end; the unconnected-output printing rule; printing being incremental — a value reaches the terminal before the run ends; the error paths above ending non-zero with a readable message. The workspace builds and passes `cargo test` and `cargo clippy` cleanly.
- DEVELOPMENT.md describes how to build and run the fizzbuzz headless demo and the checks.
