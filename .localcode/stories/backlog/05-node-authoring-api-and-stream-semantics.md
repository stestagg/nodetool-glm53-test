## Description

Story 01 gave node types their descriptors but deliberately no behaviour; story 02 named the types values carry; story 04 turns graph files into compiled graphs that are runnable in shape but have nothing to run. This story supplies the missing half: the API a plugin author implements to give a node type its behaviour, and the stream semantics that behaviour programs against. The vision leaves the stream API as an open question for this story to settle deliberately, in the open — and everything downstream inherits the settlement: the engine (06), the events observer (07), and every plugin from the utility library (08) on.

The user here is the plugin author. The outcome: implement your node's behaviour once, against one small uniform surface, and the engine later drives it with no per-node special cases, because the semantics were defined once, here. The settled semantics, and why:

- **New value vs current value (REQ-18).** Each input presents both faces: its *arrivals* — every new value in order, then completion — and its *held current value*, the latest value seen, readable at any time and surviving that input's completion. Awaiting arrivals and reading the current value are the two primitives everything else composes from.
- **Multi-input arrival.** An arrival on any input triggers the node's processing once, pairing the arrival with the held current value of every other input, gated until each input has delivered its first value. Zip is rejected as the default because it starves on constants: a constant is just a stream that yields once and completes (REQ-17), and pairing the second value of a counter against a completed constant would never happen. Per-input independent handling is rejected as a second default because every node the requirements name (Condition, If, Format, Output) wants the pairing; an author whose node genuinely needs something else consumes the arrivals directly from the same primitives — one mechanism, one default, no parallel path (REQ-2).
- **Completion (REQ-19).** Completion is a stream ending: "no more data may still arrive". The default node completes when every input is complete and every arrived value has been processed (REQ-23); a node whose own logic is done may complete earlier; when a node completes, its outputs end, so completion propagates and story 06's run-finishes rule (REQ-22) rests on it. A source node — no inputs, or logic producing on its own schedule — drives itself and completes when exhausted; a constant is nothing more than such a stream that yields once and completes.
- **Backpressure.** Values cross between an emitting node and each connected downstream input through a bounded hand-off: emitting waits while the hand-off is full, so a fast producer cannot outrun a slow consumer into unbounded memory. One policy for all connections, no author-facing knobs; the accepted trade-off — a slow consumer delays its upstream node, and with it that node's other consumers — is safe because compiled graphs are acyclic (compile-checked in 04), so waiting cannot cycle (REQ-16, REQ-2).

One runtime value representation carries everything that travels — base scalars, plugin custom types, parameter literals from graph files — each value carrying its type's identity, with behaviour code reading values as the concrete Rust types its ports declared, and core unable to see inside a custom type beyond its registered metadata (REQ-32, REQ-33). The conversion functions story 02 declares and the parameter literals story 03 parses are written against this same representation; that is the seam both stories deliberately left to this one.

Behaviour failures are raised, never swallowed: an error a node's behaviour surfaces propagates on the run path (REQ-71). What a *run* then does mid-error — fail fast or isolate and drain — is story 06's decision; the authoring API only guarantees the error arrives.

Single-node execution is where this story proves itself: the engine that instantiates and wires whole graphs is story 06, so here the semantics are proven one node at a time — focused tests, plus a terminal-visible example run for the plugin author this story serves.

## Definition of done

- A node author implements behaviour for their node type through the one registration path — descriptor (01) plus behaviour (05) together make the whole node type — with no second behaviour mechanism, and the driver treats every node identically, never branching on which node a behaviour belongs to. (REQ-5, REQ-43, REQ-8, REQ-73)
- One runtime value representation carries every value on every stream — base scalars, plugin custom types, parameter literals — identified by its type's id, read and produced by behaviour code as the concrete Rust types its ports declared; core cannot inspect a custom type's payload beyond its registered metadata. (REQ-32, REQ-33)
- Each input exposes arrivals and current value: awaiting the next arrival yields each new value exactly once, in order, then completion; the current value is the latest held value, none before the first arrival, still readable after that input completes. A stream that yields once and completes is a first-class case indistinguishable from any other stream — no distinct constant plumbing. (REQ-18, REQ-17)
- An arrival on any input triggers the node's processing once, pairing against the held current value of every other input, gated until each input has delivered a first value; each arrival is one trigger — no batching, no barrier (REQ-16). An input that never delivers (unconnected, no parameter) is the degenerate stream: it completes immediately and never fires the node. A behaviour needing different arrival semantics consumes arrivals directly from the same input faces. (REQ-18)
- Completion follows the stream: a node completes, by default, when every input is complete and every arrived value has been processed (REQ-23); a node may complete earlier when its logic is done; on completion its outputs end, so no downstream input ever waits on a completed node for further values — the base on which story 06 builds run completion. (REQ-19, REQ-22)
- A value emitted to an output is delivered to every connected downstream input; fan-out is the engine's routing, not the author's concern. (REQ-20)
- The hand-off between an emitting node and each downstream input is bounded; emitting waits while the hand-off is full; memory stays bounded when a consumer is slower than its producer; capacity is one fixed policy with no author-facing knobs. (REQ-2, REQ-16)
- A behaviour's error propagates on the run path and is never swallowed into a silent skip or a dropped value. (REQ-71)
- Focused tests execute single nodes against scripted streams covering: per-arrival triggering with held-value pairing; first-value gating; a held value surviving its input's completion (the constant case); default completion after the last value on completed inputs; early completion by node logic; a self-driving source completing after its last value; the empty-input degenerate; one emitted value delivered to two downstream consumers; backpressure making a producer wait on a stalled consumer; error propagation; and a union-declared port receiving different declared types through the one value representation. The workspace builds and passes `cargo test` and `cargo clippy` cleanly.
- The example binary from the core story shows a node with real behaviour from a terminal: an example plugin declares a small node via the authoring API, the example drives it with a scripted two-input stream including a one-value-then-complete stream, and prints each emitted value as it arrives and the node's completion. Running it is the visible proof. (REQ-43)

## Comments

- 2026-09-16 — Scope seams: instantiating compiled graphs into running ones — node tasks, wiring, run lifecycle, and mid-run error behaviour (fail fast vs drain) — is story 06; the events observer and node status reporting (the status half of REQ-43) are story 07. This story delivers the behaviour API and its driver, which 06 instantiates per node instance. (REQ-74)
- 2026-09-16 — Story 02's comment left "whether numeric-generic nodes (REQ-62) pick it up" to this story: what settles here is the value-level capability — one value representation carrying any registered type, so a node whose ports declare a union of numeric types can receive every one of them through it. Making that ergonomic for the author (helper macros, per-plugin utilities) is plugin territory, settled with the fizzbuzz nodes in story 09 — core gains nothing type-specific. (REQ-73)
- 2026-09-16 — Pairing rationale, once more from the requirements' own example: Condition pairs a counter against a constant threshold; the constant completes after one value, so any zip-like default would stop pairing after the first comparison. Pairing against the held current value is the only default under which constants need no special treatment — which is what makes "constant values can appear constant" (REQ-17) true rather than aspirational.
- 2026-09-16 — The degenerate empty input (neither connected nor parameterised) completing immediately means such a node never fires and completes — honest, uniform semantics. Whether compile time should flag inputs left neither connected nor parameterised is a compile-time question story 04 owns; this story only fixes what happens at runtime should such a graph compile.
- 2026-09-16 — Backpressure is bounded hand-off with waiting sends rather than unbounded queues: bounded memory is worth the coordination, and the DAG guarantee (compile-checked in 04) is what makes waiting safe. Capacity is deliberately not an authoring knob — one policy, so the author's mental model stays "emit and it flows, unless my consumer is slow".
