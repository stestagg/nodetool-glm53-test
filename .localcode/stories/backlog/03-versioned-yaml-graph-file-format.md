## Description

Core can list node types (story 01) and name the types values carry (story 02), but nothing yet says how a *graph* — instances of those types, wired together — exists as something a user can write, keep, and hand to the tool. This story makes graphs plain files: the one static document a headless run loads and the visual editor opens, the same shape in both experiences.

A graph file is hand-writable YAML. It carries a schema version field, an optional name, the graph's nodes, and its edges. Each node is an instance, not a type: it has its own uuid, a type reference naming which registered node type it instantiates, an optional user-chosen label overriding the type's default, parameter values for inputs the user wants to fix as literal values, and a metadata mapping attached to the node for visual bookkeeping — layout position and the like — which the tool carries along but the engine never reads. Edges run from an output to an input: an input takes at most one upstream, an output may feed any number of downstream inputs. Every input is expressed exactly one of two ways — connected by an edge, or holding a parameter value written as a plain YAML scalar — which is precisely the choice the editor's inline scalar fields will later present.

Loading is structural, and deliberately no more. The loader checks the document's shape: well-formed YAML, nodes and edges where they belong, edges pointing at nodes that exist in the file, at most one upstream per input, unknown fields reported, a schema version the reader knows. Whether a referenced node type exists in the registry, whether ports line up, whether a connection's types are compatible — none of that is loading's business; compile time decides (story 04), and a file referencing types this binary never linked still loads. What loading does guarantee is honesty about failure: a file that fails to load fails loudly and precisely, the error naming the offending node, edge, or field and where it sits, nothing guessed, defaulted, or silently dropped. A typo'd field name is an error rather than a quietly ignored key, because a hand-writer's silently lost layout position must never look like success. Graph files are untrusted input at a parse boundary: reported, never a crash.

Round-tripping is the quiet heart of the story: what one tool writes another reads back unchanged. A graph sketched by hand in a text editor is the same artefact the editor later saves (story 15) and the headless run consumes (story 06); hand-written and tool-written files are interchangeable without ceremony.

## Definition of done

- A graph definition is a plain YAML file, writable by hand in a text editor with no UI and no tooling, carrying a schema version, an optional name, node instances, and edges; core loads it without any UI involved. (REQ-11)
- Each node in the file is an instance carrying: its own uuid, the type reference of the node type it instantiates, an optional user label overriding the type's default label, parameter values for inputs fixed as literals, and a per-node metadata mapping for visual information such as layout position, attached to the node and carried verbatim. (REQ-41, REQ-40, REQ-12)
- Edges run from an output to an input; the format expresses an input having at most one upstream connection and an output feeding any number of downstream inputs. (REQ-21, REQ-20)
- Every input is expressed as exactly one of: connected by an edge, or holding a parameter value written as a plain YAML scalar (boolean, integer, float, or string); which scalar type a literal is and whether it suits the port are settled at compile time, not load. (REQ-57)
- Loading is structural and plugin-independent: a file loads with no node types registered at all, and no type, port, or connection check happens at load — that enforcement belongs to compile time (story 04), and a run never starts on a broken graph because compilation is where it stops. (REQ-60, REQ-72)
- A file that fails to load fails with a clear error naming the problem and its location — malformed YAML, wrong document shape, an edge referencing a node not in the file, more than one upstream on an input, a field the schema does not know, a schema version the reader does not support — with no silent defaults and no dropped content; a malformed file never crashes the process. (REQ-71)
- A load–dump round trip preserves the file's meaning exactly: uuids, labels, parameter values, metadata, and edges come back as they went in, so hand-written and tool-written files are interchangeable. (REQ-11)
- An example binary in the workspace loads the sample graph files shipped with it and prints what it loaded — for each node its uuid, type reference, label, parameters, and metadata, then the edges — dumps one back to YAML showing the round trip, and attempts a deliberately malformed file showing the resulting error; running it from a terminal is the visible proof. Focused tests cover round-trip fidelity and each structural error path, and the workspace builds and passes `cargo test` and `cargo clippy` cleanly. (REQ-74)

## Comments

- 2026-09-16 — Scope seams, so this stays a format story and nothing arrives early: compile-time validation (type references resolvable, ports exist, connection types across unions and conversions) is story 04; the headless run that loads, compiles, and executes is story 06; the editor's open/save and keeping metadata current is story 15. How parameter literals travel at runtime is the value representation of story 05. Parameter literals in this story are the core scalars; a custom type's file representation arrives with the plugin that owns it, via its own ser/de (story 21). (REQ-7, REQ-34 land with those stories, not this one.)
- 2026-09-16 — What lives in parameters vs metadata, settled here as the vision asked: parameters are the values the graph computes with — one per input, either an edge or a literal; metadata is everything the engine may ignore, starting with layout position. The split follows one question: would the run be wrong without it? If yes, it is a parameter or an edge; if no, it is metadata.
- 2026-09-16 — Versioning: a single schema version field the reader checks; an unsupported version is a clear error, and there is no migration tooling — the vision deliberately leaves it at that. Unknown fields are errors rather than ignored keys, chosen for the hand-writer (a typo should be visible, not silently swallowed); forward compatibility rides the version field, so nothing newer can slip past unnoticed anyway.
- 2026-09-16 — Groups leave room without being built: the schema stays uniform — a node is a node, referenced by type reference — so a group will enter as an ordinary node instance whose type reference names a group type, and its nested definition must slot into the same document without reworking the schema or breaking existing files. Nothing here assumes flatness; the subgraph representation itself is story 23's to settle. (REQ-44)
- 2026-09-16 — Metadata is opaque by design: core carries it verbatim, the engine never branches on it, and the editor owns what it stores there — the same "core stays abstract" line as everywhere else. (REQ-73)
