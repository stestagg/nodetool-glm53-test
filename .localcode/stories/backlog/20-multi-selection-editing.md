## Description

Story 12 gave the canvas its first selection: one node at a time, moved by its title bar. Building real graphs means arranging them in batches — nudging a pipeline stage aside, deleting a clump that didn't work, setting the same parameter on five nodes at once — and doing each of those one node at a time is exactly the ceremony the Blender reference avoids. This story adds the selection layer over the gestures 12–14 delivered: shift-drag rectangle selection, group moves, selection-wide delete, and the sidebar's behaviour when several nodes are selected — settling, as the vision's open question asks, how it chooses which fields to show.

The selection model:

- **Marquee**: shift-click-drag on the background draws a rectangle; every node inside or intersecting it joins the selection. Plain background drag stays panning (REQ-51) — the two background drags differ by Shift alone. The marquee selects nodes, never wires: edges are not selection targets, their fates ride with their nodes.
- **Toggle**: shift-click on a node adds it to, or removes it from, the current selection. Plain click selects that node alone and clears the rest; plain background click clears the selection entirely.
- Any non-empty selection opens the sidebar; emptying it closes it — story 14's open/close rule, unchanged.

**Group moves**: while more than one node is selected, dragging any part of any selected node moves the whole selection — REQ-53's "anywhere if multi-selected" — every selected node following the pointer for the duration of the drag, one commit landing where each rests. Single nodes keep story 12's title-area drag. **Delete**: pressing Delete (or Backspace) removes every selected node, each with every edge attached to it cascaded — story 13's deferral, the same no-dangling-edges guarantee as one-node delete, applied to the group.

The sidebar with several nodes selected shows a short header naming the selection — how many nodes — and then only the common parameter fields. A field is common when every selected node's type declares an input of that name which is scalar-possible by story 14's rule and unconnected on every selected node; everything else — labels, uuids, type references, connected or non-scalar inputs, fields only some of the nodes have — is not shown, because the sidebar edits stored values and only these are held in common. A common field shows its value only when every selected node holds the same one; when they differ it shows a distinct "mixed" state, the field blank. Committing applies the typed value to every selected node; committing an empty field unsets it on every selected node; Esc discards — story 14's commit rules inherited whole. When the selection has no common fields at all, the sidebar says so plainly rather than sitting silently empty. Labels are deliberately not editable in a multi-selection: a label names one node, and a gesture that stamped one shared name across a group destroys the orientation labels exist for.

Unknown-typed placeholder nodes (12) take part in selection, group moves, and group delete — uuid-addressed operations need no type knowledge — but contribute no common fields, their ports unknown.

No new operation messages: the selection is a view-side convenience that fans out to the existing catalogue — a group move sends the existing move operation once per node, a group delete the existing delete operation once per node, a common-field commit the existing parameter edit once per node — the same precedent as 13's "rewiring is wire with replace semantics". The server neither knows nor cares that a selection existed; its error answers stand as in 11 and 14 — a stale tab's commit for an input that has since been wired is refused, the definition untouched, the connection usable. Selection itself is per-view state, like scroll position: a selection in one tab is not in another; the changes made through it are server state like any edit and appear everywhere.

While a run is on (16), marquee and toggling stay live — looking is not editing, and a selection is not an edit — while group moves, group deletes, and common-field commits go quiet with every other editing gesture.

Deliberately not here: align/distribute or snapping aids; copy-paste; box-selection of edges; group/subgraph packaging (23); the keyboard operability pass (22). Nothing is validated at edit time beyond the structural refusals 14 already makes — enforcement is compile time's (REQ-60, REQ-72).

## Definition of done

- Shift-click-drag on the canvas background draws a visible rectangle and every node inside or intersecting it joins a visible multi-selection; shift-click on a node toggles it in or out; plain click selects one node and clears the rest; plain background click clears the selection; the sidebar opens for any non-empty selection and closes when the selection empties. The marquee selects nodes only, never wires. (REQ-55, REQ-56)
- With several nodes selected, dragging any part of any selected node moves the entire selection — all selected nodes follow the pointer for the duration of the drag and one commit lands where each rests, positions recorded in node metadata through the existing server-applied operation path; a single selected node keeps story 12's title-area drag. (REQ-53, REQ-12)
- Delete (or Backspace) with a multi-selection removes every selected node from canvas and definition together with every edge attached to any of them, leaving no dangling edges. (REQ-2)
- With several nodes selected, the sidebar shows a header naming the selection and only the common parameter fields — an input declared scalar-possible by every selected node's type and unconnected on every one of them — the value shown only when all selected nodes hold the same value, a distinct mixed state otherwise; committing applies the value to every selected node, committing an empty field unsets it on every one, Esc discards; with no common fields the sidebar says so plainly; no label editing and no uuid/type block in the multi-selection sidebar. (REQ-56, REQ-47)
- Marquee, toggle, and clearing the selection stay available while a run is on; group moves, group deletes, and common-field commits are inert in the UI, and any edit operation arriving while running is rejected by the server like every other. (REQ-24, REQ-25)
- The server receives no new message kinds: a group move, delete, or common-field commit arrives as the existing per-node operations, applied and pushed as in 12–14; a parameter edit arriving for a since-connected input is answered with 14's error, the definition untouched, the connection usable. Selection is per-view state: a second tab shows the same graph, not the same selection, and a change made through a selection in one tab appears in the other. (REQ-2, REQ-45)
- Focused tests cover the fan-out path: a group move updating every named node's position in metadata; a group delete cascading every selected node's edges; a common-field commit written to every named node and an empty commit unsetting it on every one; the refusals standing when a named input is connected or a named node is missing from the definition. The workspace builds and passes `cargo test` and `cargo clippy` cleanly, with the UI build part of the check set DEVELOPMENT.md documents.
- The visible proof, run per DEVELOPMENT.md: drop a row of nodes, marquee three, drag one of them anywhere on its body and watch all three travel together; shift-click a fourth in and out of the selection; select two nodes sharing a scalar input, type a value into the sidebar field and see it land on both, then set one to a different value first and see the mixed state before committing; press Delete with three selected and see the nodes and their wires go together; reload and see the graph with the selection gone; start a run and check the marquee still selects while a group drag does nothing.

## Comments

- 2026-09-16 — Scope seams: no additions to story 11's message catalogue — the selection fans out to 12's move, 13's delete, and 14's parameter edit, one operation per node, the precedent 13 set with rewiring. Multi-select delete was 13's explicit deferral here; the common-fields sidebar was 14's; 16 reserved selection as live while running. Copy-paste, alignment aids, edge marquee, and group packaging (23) are out; keyboard operability of these gestures is 22's pass. (REQ-74)
- 2026-09-16 — UX calls settled here, answering the vision's open question on the multi-selection sidebar: common fields only, chosen by a rule the browser reads off the listing — same input name everywhere, scalar-possible everywhere, unconnected everywhere — so core never branches on what a node is (REQ-73) and a plugin's nodes join groups for free by declaring scalar ports (REQ-38). No group rename, per the description. The mixed state is shown rather than silently committing blank or displaying one node's value as if shared — either would lie about what a commit would do. Empty-commit-unsets is inherited from 14 so clearing a group's parameter is one gesture, consistent with empty-means-unset everywhere else.
- 2026-09-16 — Why no new messages: the user-visible behaviour — one drag, one Delete, one field commit — is identical either way, and per-node operations keep one mechanism for each edit kind (REQ-2); whole-definition pushes (12) make the fan-out cheap for a local single-user tool, and selection stays per-view state so nothing about it needs the server's participation.
